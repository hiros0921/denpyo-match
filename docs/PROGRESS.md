### この段階で踏んだ失敗

**① std::regex はバイト単位で動く**

`[年/\-\.]` と書いたが、年 は3バイト（E5 B9 B4）なので「そのいずれか1バイト」の
意味になる。E5 に一致した後 B9 B4 が数字でないため失敗し、日付が 0/20 だった。
区切りを先にASCIIへ置き換えてから正規表現をかける形に直した。

**② Tesseract のブロックは重なる**

日本語には単語の区切りが無いため、単語矩形が隣どうしで食い込む。

```
x=121 w=208 [ハル]   ← x 121〜329 を占める
x=178 w=41  [タ]     ← 前のブロックの内側から始まる
```

「隙間が負なら別項目」と書いたため、重なるブロックを全部捨てて
「ハル」しか取れていなかった。行ごとにx順で並べ、重なりを許す形に直した。

**③ 抽出側でしきい値を引いたのは誤り**

「確信が持てなければ返さない」（最低スコア0.4）を入れたところ、
照合の正解が 12/20 → 10/20 に落ちた。正しい抽出まで捨てていた。

このプロダクトには「要確認」の仕組みがある。**抽出の段階で線を引くと、
現場が調整できなくなる。** 確信の低いものは低い信頼度を付けて返し、
どこで人が確認するかは閾値設定に委ねる。撤回した。

**④ 人が読む表を機械で解析しようとした**

評価スクリプトが照合結果を 0/20 と報告し続けたが、照合エンジン自体は
正しく動いていた。見出し行と指数表記（1e+02）を名前として切り出していた。
`dm_match --json` と `dm_ocr --json` を用意して解決した。
**Go から呼ぶときも同じ問題が起きるので、この対応は第6段階の前提でもある。**

人が見直せば救える。閾値シミュレーションはこの調整のためにある。

### 三分岐の根拠

第5段階の実測（正解の照合スコア平均88.2 / 不正解33.4、70で分離）にもとづき、
既定を 上限95 / 下限70 とした。**この値を回帰テストに固定してある**ので、
既定を変えると `TestDefaultMatchesMeasurement` が落ちる。

### 開発中のパス問題（解決）

当初 `WorkDirHost`（Goが作る）と `WorkDirContainer`（C++に渡す）を分けていたが、
**そもそも `/tmp` はコンテナと共有されていなかった。**

colima が Mac と共有しているのは `$HOME` だけ。`/tmp` は VM の中に別に存在する。
C++ どうしのやり取りだけなら VM 内の `/tmp` で完結するので動いてしまい、
Go がファイルを書いて C++ が読む段になって初めて表面化した。
エラーは「書いたはずのファイルが無い」という形でしか出ない。

作業フォルダを `$HOME` の下（`denpo_match/.local/`）に移し、コンテナにも
**同じ絶対パス**で見せることにした。両側でパスが一致するので、対応表が要らなくなる。

### 【重大】監査ログの検証が中身の書き換えを検知できていなかった

`verify_audit_chain()` は「prev_hash が直前行の row_hash と一致するか」しか
見ておらず、**row_hash を中身から計算し直していなかった。**

ルールとトリガを一時的に外して「DBに直接繋がれた」状況を作り、実測した。

```
書き換え前  id=100  after={"score":100,"partner_id":10,...}
書き換え後  id=100  after={"score":999}
見つかった異常  0件   ← 検知できていない
```

連鎖を持たせた目的は「後から書き換えられたことを検知する」ことなので、
これでは仕組みとして成立していない。作り直した結果:

```
① 中身だけ書き換え    検知した  「中身がハッシュと一致しない」
② 実行者の差し替え    検知した  「中身がハッシュと一致しない」
③ 行の削除           検知した  「直前行との連鎖が切れている」
```

**同時に見つかった別の問題。** 元の式は材料に `occurred_at::text` を使っていた。
timestamptz を text にすると接続の TimeZone 設定で描画が変わるので、
書いたときと検証するときで設定が違えば、改竄が無くても不一致になる。
UTC の固定書式に変えた。

式を変えると既存行のハッシュが合わなくなるが、監査ログは追記のみで
書き直す手段が無い（それが正しい）。`hash_version` を持たせ、
行ごとにどの式で作られたかを記録するようにした。運用開始後に同じことが
起きても、版を足すだけで対応できる。

```
version 1  元の式。繋がりだけ検証できる
version 2  中身から計算し直せる。時間帯に依存しない
```

### この段階で踏んだ失敗

**① 支払いが失敗しても止まらなかった（最も重い）**

`invoice.payment_failed` を受けて猶予の終わりだけを書き、状態は `active` のままにしていた。
`billing.Evaluate` は active を見て素通しするので、猶予が切れても止まらない。

実際の Stripe は `past_due` への変化も別途送るが、**届く順番は保証されない**。
片方だけ届いた時点で「active なのに猶予がある」という辻褄の合わない行ができる。
猶予を書くなら状態も合わせる、という形に直した。

**② API 版の食い違いが「署名エラー」に見えた**

```
アカウント既定    2026-07-29.dahlia
stripe-go v82    2025-08-27.basil
```

この状態だと鍵が正しくても全イベントが弾かれる。しかもエラーは
「署名が正しくありません」なので、鍵の設定を疑って時間を溶かす。
版が一致する v86.2.0 に上げ、エラーの文言も分離した。

**③ `ON CONFLICT` の式を `VALUES` 側にも使っていた**

猶予の式に `coalesce(subscriptions.grace_until, ...)` を使い、
それを INSERT の VALUES にも渡していた。新規行にはまだ参照先が無いので
`invalid reference to FROM-clause entry` で Webhook が全部500になった。

**④ Turbo が外部への302を追わない**

`redirect_to stripe_url, allow_other_host: true` はサーバー側では正しく動くが、
Turbo が遷移を止めるので**押しても何も起きない**ように見える。
`form: { data: { turbo: false } }` が要る。
Rails 8 と Stripe の組み合わせで必ず踏む。

**⑤ テストの偽イベントが本物と形が違った**

`"object": "event"` と `api_version` を入れていなかった。
実際の Stripe は必ず付けてくるので、試験でも同じ形にする。

**閾値では防げない。** 100が最大値なので、上限をいくら上げても止まらない。

### 原因は前処理だった

```
元画像     バルタ商会284   ← 284 が読めている（ハ→バ の誤読はある）
前処理後   ハルタ商会      ← 284 が消えて、別会社と完全一致
```

第5段階で「前処理はOCRの精度を上げなかった」と記録していながら、
前処理後の画像を渡し続けていた。100枚で測り直したところ、
**上げないどころか下げていた。**

```

取引先名が一致           52枚               54枚
伝票番号が一致           77枚               92枚   ← 15枚の差
金額が一致               93枚               98枚
```

20枚では差が見えず、100枚で初めて出た。

### 直した3点

**① OCRには元画像を渡す**

前処理そのものは捨てない。傾き検出・セル検出・人が見る画像として使う。
OCRに渡すのをやめるだけ。

**② 候補がゼロのときだけ、前処理後の画像で読み直す**

劣化の強さで役割が分かれていた（候補生成に正解が含まれた枚数）。

```
劣化      前処理してから   元画像    どちらかで届く
light        19 (70%)     19 (70%)    23 (85%)
normal       28 (82%)     28 (82%)    30 (88%)
heavy        32 (82%)     29 (74%)    37 (95%)
合計         79 (79%)     76 (76%)    90 (90%)
```

重い劣化では前処理が効く。軽い劣化では元画像が良い。

**【重要】「スコアの高いほうを採る」にしてはいけない。**
前処理は名前の末尾を消すことがあり、消えた結果が別の実在する会社と
完全一致するとスコア100（最大値）になる。高いほうを採ると、
その誤りを必ず選ぶ。

元画像で候補が出たならそれを信じ、**出なかったときだけ**前処理後を試す。
上書きが起きるのは「何も無い」ときだけなので、
正しい結果を誤った結果で壊すことが構造上ありえない。

**③ 「御」から後ろを切る**

却下された伝票の読み取りに規則性があった。

```
ヤマト運輸335(株)御』of     ← 御中 の誤読が名前にくっついている
帆ナンセイサービス御Fnre
(有)シラカワ運輸御』o
```

「御中」を除くコードは既に入っていたが、**2文字での一致では効いていなかった。**
実際に多かったのは中側が壊れた形なので、2文字だと一致しない。
「御」1文字を見つけたら、そこから後ろを全部落とす。
日本の会社名に「御」が現れることは、まず無い。

あわせて、日本語を含む名前の末尾に残った英字も落とす（…(株)4a）。
先頭の英字は落とさない。ABC商事のような社名が実在するため。

### ④ 先頭一致を、先頭＋末尾の半々にする

却下された伝票を調べると、**先頭の1文字が壊れただけで20点が消えていた。**

```

  編集距離 0.875 / n-gram 0.857 / 先頭一致 0.000 → 合計 69.5
```

先頭一致は「先頭から何文字一致するか ÷ 長いほうの文字数」なので、
1文字目が違えば 0.000 になる。重み0.2＝20点が丸ごと失われ、
下限70に0.5点届かず却下されていた。

**第4段階で「日本語の企業名を識別しているのは末尾（運輸／建設／商事／電機）」と
実測しながら、指標は先頭のままだった。** 重みを下げただけで中身を変えていなかった。

末尾一致を実装し、100枚で重みの組み合わせを総当たりした（cmd/weightsweep）。


別会社との差が広がることも確認した。

## 第9段階の追記：Vision の実装（仕様の穴を塞いだ）

### 見つかった穴

`clients.ocr_engine` に `vision` を設定できるのに、Vision が実装されていなかった。
さらに悪いことに、`dm_ocr --engine vision` は**引数を受け取るだけで中身を見ておらず、
黙って Tesseract で動いていた。**

顧問先が「精度優先で Vision」と設定しても実際は Tesseract が動き、
記録にも tesseract と残るので、設定が効いていないことに気付く手がかりが無い。

### 実装

```
core/src/ocr/main.cpp      --engine vision を明示的に拒否（黙って別物を動かさない）
                           --extract を追加（標準入力のブロックから抽出だけ行う）
api/internal/core/vision.go   Google Cloud Vision（REST直・SDKなし）
api/internal/pipeline/        エンジンを顧問先ごとに切り替え
api/internal/store/           Claim が clients.ocr_engine を返す
```

### 設計の要点：抽出は1つに保つ

「どれが取引先名か・日付か・金額か」を決める規則（御中の左・上部左・
法人格を含む…）は C++ に積み重なっている。Vision 用に Go へ書き直すと
実装が2つになり、片方だけ直せば必ず食い違う。食い違っても例外は出ない。
「Vision にした顧問先だけ精度が落ちる」という形でしか表面化しない。

そこで `dm_ocr --extract` を作った。Vision が読んだブロックを標準入力で渡し、
抽出は C++ の同じ実装を通す。同じブロックを渡せば同じ結果が出ることを確認済み。

### 設定漏れは「止まる」形で出す

Vision 未設定のまま vision の顧問先が伝票を入れると、
黙って Tesseract に落とすのではなく、現場が読める理由つきで止まる。

```
OCRで失敗: この顧問先は Vision を使う設定ですが、Vision の設定がありません。
顧問先の設定を tesseract に変えるか、APIキーを設定してください
```

起動時にも、vision の顧問先がいるのにキーが無ければ警告を出す。

実測での確認:

```
vision の顧問先     理由つきで止まる（試行2回、上の文言）
tesseract の顧問先  影響なし（自動承認まで完了）
```

### Google Cloud の設定（完了・諏訪さんの作業）

```
プロジェクト denpo-match / 予算 月1,000円（50%・90%・100%でアラート）
Cloud Vision API を有効化
APIキーは Cloud Vision API のみに制限
```

予算の範囲は「すべてのプロジェクト」から denpo-match だけに絞るよう案内済み。
「アラートのみ」は課金を止めない（メールが来るだけ）ことも説明済み。
本当に止めるなら Vision の割り当て（Quota）で1日あたりの上限を設定する。

### Vision で100枚（Tesseract との比較・同じ画像）

```
              Tesseract   Vision
自動承認          68        96
  うち誤承認       0         0
要確認            20         1
却下              12         3
1位が正解         88        97

スコア分布（Vision）
  正解 96件   最小 70.2 / ほぼ全て 100
  不正解 3件  最大 66.4          → 完全に分離
```

**人が見る枚数が 32枚 → 4枚。** 費用は約0.22円/枚（月1,000枚まで無料）。
事務所の人件費と比べれば、Vision を既定にする価値は明確。
機密性を気にする顧問先だけ Tesseract、という当初の設計どおりの構図になった。

### この過程で踏んだ失敗（Vision 編）

**① Go 側の並べ替えが読み取りを壊していた**

Vision で1件だけ誤承認が出た（(株)ハルタ物産512 → 512 が消えて
「ハルタ物産(株)」という実在の別会社と完全一致、スコア100）。

Vision の生の応答を確認すると **512 はブロックとして正しく存在した**。
同じブロックを抽出（dm_ocr --extract）に渡すと:

```
Vision の元の順       (株)ハルタ物産512   正しい
Go の並べ替えを通す    (株)ハルタ物産      512 が落ちる
```

原因は Go 側に書いた「上から下、同じ行なら左から右」の並べ替え。
「Yの差が小さければX比較」という比較は推移律を満たさず、順序が乱れることがある。
そもそも行まとめと並べ替えは C++ の抽出側に既にあり、二重で、壊し得るだけだった。
削除して解決。**修正後の100枚で誤承認ゼロを確認。**

教訓: エンジンを差し替えるときは「読む」と「解釈する」の境目に
余計な加工を挟まない。加工するならその層は1つに保つ。

**② 金額の読み取りが 66/94 しか合っていなかった**

1件の異常値を追ったつもりが、100枚で測ると **28件が誤り**だった。
1件だけ見て「異常値がひとつ」と書いたのは、測っていなかったから。

誤りには明確な規則性があった。

```
読み取り        正解        差
88209000        882090      末尾に "00"
1395350000      1395350     末尾に "000"
376750 8        376750      末尾に "8"
952160888       952160      末尾に "888"
```

Vision が返した語そのものが `882,090-00` だった。
生成データは `¥882,090-` と書いている。**日本の帳票の慣習で、
末尾のハイフンは「これ以下の端数は無い」を表す終端記号**であり、
金額の一部ではない。切らずに数字だけ抜いていたため、
ハイフンの後ろに続いた文字の数字まで混ざっていた。

数字のあとに来る `-` で切るようにした（数字より前の `-` は切らない。
マイナス記号や、罫線を `-` と誤読したものが先頭に付くため）。

```
金額の一致  66/94 → 91/94
```

**③ 日付を金額として拾っていた**

`2026年5月25日` から数字だけを抜くと 2026525 になり、7桁の数字として
金額の候補に入る。手がかり（合計の右・通貨記号）が無い伝票では、
これが最高点になって採用されていた（inv_0004）。
日付として解釈できるブロックは金額の候補から外した。

**ただしこの修正は、この100枚では差し引きゼロだった**（1件直り、
別の1件が入れ替わりで誤りになった）。論理的には正しいので残すが、
数字が動かなかったことは記録しておく。

### 項目ごとの精度（Vision・100枚）

```
伝票番号が一致   94 / 100
金額が一致       91 / 94   （66 → 91）
日付が一致       89 / 94
```

**三分岐は取引先の照合スコアだけで決まる**ので、これらの誤りは
誤承認に直結しない。金額の突合（会計データとの照合）を実装するときに、
残る3件の性質を詰める。

## 閾値の根拠を100枚で出し直した（受領側対応後）

上限95/下限70は20枚時点（第5段階）の値だった。受領側の抽出改善
（発行元/宛先の分離・数字と日付の除外・発行元ブロックの除外）を入れた後の
コードで、同じ100枚を Tesseract と Vision の両方で流し直した。

### 分布（1位のスコア）

```
              1位が正解                          1位が不正解
Tesseract    91件  19.3, 19.3, 41.4, 52.1,       3件  8.1, 23.8, 26.0
                   73.1, 74.0〜（ここから密集）
Vision       99件  62.9, 66.4, あとは全て100      1件  50.9
候補ゼロ     Tesseract 6件 / Vision 0件
```

20枚時点と比べて、不正解の最大が 52.1 → 26.0（Tesseract）に下がった。
自社名や金額を取引先名として照合していた誤りが消えたため。

### 却下13件の内訳（Tesseract・旧下限70）

```
候補ゼロ           6件   読み取りが に中 / MASLME / WYNALS など。
                        名前になっていないので候補が出ない。正しい却下。
                        ※Vision は6件とも読めた。エンジンの差で、閾値では直らない
正解だが下限未満   4件   19.3 ×2, 41.4, 52.1
不正解で下限未満   3件   8.1, 23.8, 26.0
```

### 既定値の変更: 下限 70 → 55（上限95は据え置き）

しきい値の総当たり（100枚のスコアに対して機械的に適用）:

```
                     自動承認   誤承認   要確認   却下   正解を却下
Tesseract  95/70        67        0       20      13        4
           95/55        67        0       20      13        4   ← 変化なし
Vision     95/70        97        0        0       3        2
           95/55        97        0        2       1        0   ← 2枚を救う
```

下限55は、不正解の最大（Vision 50.9）より上、Vision の正解の最小（62.9）
より下。70のままだと Vision の正解2枚（62.9 / 66.4）を却下していた。

**上限と下限では、外したときの被害がまったく違う。**
上限は「人を省いてよいか」の線で、間違えると誤った確定が起きる。
下限は「候補を見せるか」の線で、間違えても人の手間が少し増えるだけ。
だから上限は 95 のまま大きな余裕を残し、下限だけ実測に寄せた。

なおこの100枚では上限を75まで下げても誤承認ゼロだった
（Tesseract の自動承認 67 → 82）。ただしこれは生成データでの話であり、
既定値を下げる根拠にはしない。下げる判断は、導入先が自分の実データを
閾値シミュレーションで見て行う。その画面を作ったのはこのためで、
「この100枚なら75で+15枚」はまさにその画面が出す種類の答え。

変更は decide.Default と、その根拠を固定する回帰テスト
（TestDefaultMatchesMeasurement）に入れた。DBに閾値の行がある導入先には
影響しない（既定値はDBに1件も無いときだけ使われる）。

計測の道具: cmd/pipetest に -engine と -csv を足した。
1枚ごとの明細（スコア・正誤・候補数・読み取った名前）をCSVで書き出し、
分布としきい値の総当たりはそこから出す。集計値だけでは
「不正解の最大」「正解の最小」が出ない。
