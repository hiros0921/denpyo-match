# DENPYO MATCH

会計事務所向けの帳票OCR照合システム。

受け取った請求書・領収書・レシートを読み取り、取引先マスタと照合し、
**「どの精度なら人の確認を省いてよいか」を現場が自分で決められる**ようにする。

---

## このプロダクトの中心にあるもの

OCRの精度ではない。**閾値をどこに引くかを現場が決められること**にある。

自動で処理する仕組みは、精度が100%でない限り必ず誤りを出す。
問題は「誤りが出ること」ではなく、**どれだけの誤りなら受け入れられるかを
誰も決められないこと**にある。決められないから、結局すべてを人が見る。

そこで判定を三つに分ける。

```
照合スコア ≥ 上限   自動承認   人は見ない
上限 > スコア ≥ 下限  要確認    人が見る
スコア < 下限        却下      人が見る
```

上限と下限は**コードに書かない**。DBに置き、画面のスライダーで動かす。
（コードにあるのは既定値 95/55 だけ。100枚の実測分布から出した値で、
DBに設定が1件も無いときにしか使われない。）
動かすと、過去に処理した全件を集計し直して
「この設定なら自動承認が何件、そのうち誤りが何件だったか」をその場で出す。

つまり現場は、**自分の事務所の実データで、確認を省く範囲を選べる**。
「AIが95%の精度です」と言われて信じるかどうかではなく、
自分の帳票で何件通って何件間違うかを見て決める。

閾値の変更は監査ログに残る。あとから
「この期間に緩い設定で自動承認されたものを洗い直す」ことができる。

## なぜ3つの言語を使うのか

寄せ集めではない。**それぞれに、他では代えにくい理由がある。**

### C++ — 画像処理と文字列照合

OpenCV も Tesseract も C++ のライブラリで、これらを使う以上ここは C++ になる。
加えて、この層は1枚ごとに CPU を使い切る処理なので、実行速度が
そのまま処理枚数の上限になる。

実際に速度が問題になった例:

```
100枚の処理   410.6 秒 → 27.1 秒
```

Tesseract を4並列で動かすと1本あたり7.4秒かかっていた。
原因は OpenMP の設定で、`OMP_NUM_THREADS` では直らない
（Tesseract が内部で `omp_set_num_threads()` を呼んで上書きするため）。
`OMP_THREAD_LIMIT=1` で31倍速くなった。

担当範囲:

- 前処理（傾き補正・ノイズ除去・二値化・罫線検出）
- 1枚の紙から伝票ごとの切り分け（空白の帯による分割）
- OCR（Tesseract）と項目抽出
- 取引先名の正規化と照合（レーベンシュタイン距離ほか）

### Go — 並行処理と外部プロセスの管理

複数のワーカーが同じ待ち行列から伝票を取り、C++ の実行ファイルを呼び、
結果をDBに書く。この形が最も素直に書ける。

`SELECT ... FOR UPDATE SKIP LOCKED` で待ち行列を作り、
処理中のワーカーが落ちても期限切れとして拾い直す。

C++ とは **cgo ではなくプロセス間通信**でつないでいる。理由は3つ。

1. C++ が落ちても Go は生き残る。OpenCV は壊れた画像で落ちることがあり、
   cgo だと API サーバーごと止まる
2. C++ 単体を CLI として実行できるので、問題の切り分けが速い
3. 仕様がもともと「CLIとして単体で動作すること」を求めていた

担当範囲:

- HTTP API（受付・状態照会・人の判断の記録）
- ワーカー（待ち行列・再試行・進捗）
- 三分岐の判定
- インボイス登録番号の検査
- 決済（Stripe）

### Ruby / Rails — 業務画面

会計事務所が毎日使う画面。承認キュー、閾値シミュレーション、監査ログ、
影響範囲の追跡。この種の画面は Rails が最も速く、かつ後から直しやすい。

**スキーマは Rails に持たせていない。** `schema_format = :sql` にして、
マイグレーションは `db/migrations/*.sql` に手で書いている。
部分索引・式索引・RULE・`REVOKE` といった、Rails のマイグレーションDSLで
表現できないものを使っているため。

## 設計上の判断

### 事務所を跨げないことを、どこで担保しているか

会計事務所は顧問先の帳簿を預かる仕事なので、「別の事務所のデータが見えた」は
起きた時点で終わる。ここは言葉ではなく、叩いて確かめられる形にしてある。

**当初の作りには穴があった。** API は「事務所の内側からしか呼ばれない」前提で、
認証を持っていなかった。1事務所に1台置くならその通りだが、複数の事務所で
1台を共有した瞬間に、次が全部通る。

```
GET /v1/documents/1                  伝票IDを1から順に叩けば、全事務所の伝票が読める
GET /v1/billing?organization_id=1    番号を書き換えれば他事務所の契約が読める
POST /v1/billing/portal              番号を書き換えれば他事務所の解約・カード閲覧ができる
```

**認証を足すだけでは塞がらない。** 認証は「誰が呼んだか」しか答えないので、
呼んだ側が `organization_id` を自己申告する形が残る限り、番号の書き換えは防げない。
そこで事務所IDを、本文や問い合わせ文字列に**書いてある値**から、
署名に**含まれる値**へ移した。署名を検証した時点で事務所が確定し、
以後どのハンドラも本文の `organization_id` を読まない。

```
X-DM-Org        事務所ID
X-DM-Timestamp  UNIX秒
X-DM-Signature  v1=<HMAC-SHA256>

署名対象（改行で連結）
  v1 / メソッド / パス / 問い合わせ文字列 / 時刻 / 事務所ID / 本文のSHA-256
```

そのうえで、要求が指す顧問先・伝票・職員が、その事務所のものかを毎回確かめる。
署名の検証と所有の確認は別の仕事で、片方だけでは足りない。

**同じリポジトリの中で、扱いが割れていた。**

```
ForgetAlias  AND c.organization_id = $2   「組織をまたいで消せないように」と注記付き
Approve      WHERE document_id = $1        orgID を受け取るが、監査ログにしか使っていなかった
```

`Approve` は他事務所の伝票を承認でき、しかも監査ログには**承認した側の事務所**が
残るので、記録を見ても気付けなかった。「全クエリに書き忘れないこと」は
規律であって保証ではない、という実例になったので、そのまま残しておく。

呼ぶ側（Rails）では、事務所IDをメソッドの引数ではなく `ApiClient` の属性にした。
引数だと、11か所ある呼び出しのどこか1つで `current_organization` 以外を渡した瞬間に
他事務所へ手が届く。`ApplicationController#api` からしか作れない形にして、
渡し間違える場所を無くしてある。

### テナント分離はアプリケーション層で担保している。DB層の RLS は導入していない

上に書いた所有の確認は、すべてアプリケーション層にある。
PostgreSQL の行レベルセキュリティ（RLS）は**入れていない**。

入れるなら、こうなる。

```
① organization_id を全テーブルに持たせる（21テーブル中11に無い）
② 親子を複合外部キーで縛り、子が親と違う事務所を持てないようにする
     ALTER TABLE documents      ADD UNIQUE (id, organization_id);
     ALTER TABLE document_pages ADD FOREIGN KEY (document_id, organization_id)
                                REFERENCES documents (id, organization_id);
③ 各テーブルに RLS を適用し、接続ごとに SET LOCAL app.org = '7' を置く
```

`SET` ではなく `SET LOCAL` でなければならない。`SET` だと接続を使い回したときに
前の要求の事務所番号が次の人に残る。

**入れていないのは、必要が無いからではなく、今は不要だから。**
穴は塞がっている。RLS は追加の防御層であって、無いと危険なものではない。
入れれば「アプリのコードを1行も通さずDBが拒否する」ことを実演できるようになるが、
それは今ある欠陥の修正ではなく、もう一段の話になる。
必要になった時点で、上の順で入れる。

### 監査ログは追記のみ

`RULE` で UPDATE と DELETE を禁止し、権限も `REVOKE` してある。
各行は直前の行のハッシュを含み、鎖になっている。

**鎖があるだけでは改竄を検出できなかった。**
RULE を外して1行の内容を書き換える実験をしたところ、検証は
「異常0件」と答えた。ハッシュを保存値と比較していたためで、
内容から再計算していなかった。書き直して検出できるようにした。

### 検証用の事務所は、開発DBにだけ作ること

`cmd/tenanttest` は `【検証】A事務所` `【検証】B事務所` を作る。
**この2つは、作ったら二度と消せない。**

```
audit_logs.actor_id → users.id            承認を1回でも記録すると、その職員は消せない
CREATE RULE audit_logs_no_delete ...      その監査ログは規則で消せない
users.organization_id → organizations.id  職員が消せないので、事務所も消せない
```

これは不具合ではなく、記録が動かせないことの裏返しである。
後から消せる記録に意味は無い。

**したがって、本番のDBに検証用の事務所を作らないこと。**
`tenanttest` は開発DBに対してだけ流す。伝票・顧問先まわりは実行のたびに
作り直すが、事務所と職員は残り続ける。

### 再送（リプレイ）は、5分の窓の中では通る

署名には時刻が入っており、5分を過ぎたものは 401 になる。
使用済み署名の記録（nonce）は**持っていない**。

つまり、正しく署名された要求を横取りできる相手なら、
**5分以内に限り、同じものを投げ直せる。** 実測した。

```
再送前の監査ログ  7 件
同じ署名をそのまま3回送る  → 200 / 200 / 200
再送後の監査ログ 10 件      承認が3回記録された
```

承認のように2回やると意味が変わる操作で効くので、書いておく。
防ぐには使用済み署名を憶えておく必要があり、そのためだけに
状態を持つ台が要る。今は画面と API が同じ台の中にいて、
横取りできる相手は既に台の中にいることになるので、釣り合わないと判断した。
**API を事務所の外へ出すときに入れる。**

### 前処理した画像を OCR に渡さない

第5段階で「前処理は精度を上げなかった」と記録しながら、
前処理後の画像を渡し続けていた。100枚で測り直したところ、
上げないどころか**下げていた**。

```
                前処理後   元画像
取引先名が一致     52       54
伝票番号が一致     77       92    ← 15枚の差
金額が一致         93       98
```

さらに悪いことに、前処理は取引先名の末尾を消すことがあった。
`ハルタ商会284` → `ハルタ商会` となり、これが別の実在する会社と
完全一致してスコア100で自動承認された（100枚で1件の誤承認）。
**閾値では止められない種類の誤り。**

前処理そのものは捨てていない。傾きの検出・セルの検出・人が見る画像として使う。
OCRに渡すのをやめただけ。

### 受領と発行で照合する相手が逆になる

```
発行（自社が出した請求書）  相手＝宛先。「○○商事 御中」の側
受領（他社から来た請求書）  相手＝発行元。宛先は自社
```

これは画像を見ても判別できない。どちらの様式にも発行元と宛先が
両方書いてあるので、「どちらが自社か」を知っている側でしか決められない。
OCRで当てにいくのではなく、設定として持つ。

実物のPDF5枚で確かめたところ、宛先と発行元が左右に並んでおり、
宛先側だけを見ていたために5枚とも取引先名を誤っていた
（しかも「代表」「経理部」「総務課」という役職・部署を拾っていた）。

## 入出金との突合

受領した伝票に対応する支払いが、実際にあったかを確かめる。
取引先マスタとの照合が「誰からの請求か」を決めるのに対し、
こちらは「本当に払ったか」を決める。記帳の根拠にできるのは後者。

銀行明細とカード明細のCSVを取り込む。会計ソフトの仕訳データを
起点にしないのは、順序が逆になるため。仕訳は記帳が終わった後にしか
存在しないが、このシステムは記帳そのものを助けるものなので、
「記帳を助けるために記帳済みデータが要る」という矛盾が起きる。

取り込み口はアダプタで分け、中は1つの表に寄せている。
インポーターだけ増やせば、突合ロジックは1本のまま。

### 3点で採点する

```
名前  0.40   摘要の正規化名 vs 取引先名＋学習した別名
金額  0.35   完全一致100 / 銀行のみ手数料差引（880円以内）70
日付  0.25   銀行は −5〜+45日で100。カードは同日100
```

**名前の重みを最大にしていない。** 実測すると、名前は
「初回は弱く、2回目から強い」性質を持つ。

```
摘要がカナだけの店名        名前スコア 100
カナ読み vs 漢字の名前      19〜56
人が1回承認して別名を学習   100
```

名前だけに重みを置くと、初回が全部「相手なし」になる。
金額＋日付だけで60点になる配分にしたので、名前が効かない初回でも
要確認に届き、人が確認して別名を覚えたら自動突合に届く。

```
実測  90.3（要確認）→ 100.0（自動突合）
```

### 銀行摘要は半角カナで汚れている

```
ｶ)ﾐﾗｲﾊｲｿｳｻｰﾋﾞｽ  →  ミライハイソウサービス
ﾐﾎﾝｾｷﾕｻｰﾋﾞｽ(ｶ   →  ミホンセキユサービス
```

全銀協の略号（`カ)` ＝株式会社）と取引種別の語（フリコミ・デビット）を除く。
これは **銀行摘要のときだけ** 有効にする別の設定にしてある。
通常の帳票で「カネコ商店」の頭を削ってはいけないため。

### 摘要の桁切れは、重みでは救えない

摘要は桁数制限で途中が切れる。切れると**スコアが下がるのではなく、
誤ったほうが満点になる。**

```
見本印刷工業 の摘要が12桁で切れる → ﾐﾎﾝｲﾝｻﾂ
                                  ＝ 見本印刷（別会社）と完全一致

  見本印刷（誤り）   score=100.0  lev=1.00 jac=1.00 pre=1.00
  見本印刷工業（正解）score= 51.4  lev=0.58 jac=0.55 pre=0.58
```

prefix の重みを 0.0〜0.5 で振って測ったが、**逆転件数は1件も動かない。**
誤ったほうは全成分1.00なので、配分をどう変えても100点のまま。
100点を超える配点は存在しない。

そこで対策を採点の外に置いた。摘要の正規形で始まる取引先が2件以上
あれば一意に定まらないので、名前スコアを頭打ちにして自動では確定させない。

```
崩壊点は16桁と12桁のあいだ

桁数    誤りが95以上（対策前 → 後）   16桁以上の自動承認
 8桁          3 → 0                    ―
12桁          2 → 0                    ―
16桁以上      0 → 0                101 / 111 / 115（減っていない）
```

**逆転そのものはゼロにならない。** 情報が破壊されている以上、正しい
ほうを選び直すことは原理的にできない。できるのは自動確定を止めることだけ。

### 現金は割り切る

現金取引は銀行にもカードにも載らない。レシートの多くは現金払い。
突合相手が無いものは「証憑のみ」として扱う。

画面では「相手なし」と「まだ突合していない（金額が読めていない）」を
分けて出す。混ぜると、読み取り失敗を現金取引だと誤解して調べるのをやめる。

## インボイス登録番号の照合

受け取った帳票に「T＋13桁」の登録番号が正しく載っているかを全件確かめる。
番号が無効だと仕入税額控除が取れない。つまり払う税額が変わる。

この作業は、受領した帳票にしか発生せず、全件やらなければならず、
純粋に機械的で、間違えると税額に直結する。実務では完全に手作業になっている。

判定は6段階。

```
記載なし / 形式が違う / 検査数字が合わない
形式は正しい（実在は未確認） / 登録あり / 登録が見つからない
```

**「無効」と断定しない設計にしてある。** 理由が2つある。

登録番号には2種類ある。法人番号を持つ課税事業者は `T` + 法人番号13桁だが、
個人事業者などはそれ以外の13桁で、法人番号ではない。
だから法人番号の検査数字に合わないことが、無効の証明にならない。

さらに、検査数字は9で割った余りを使うので、**0と9の取り違えを見抜けない**。
1文字だけ変えた117通りで測ったところ、115通りは弾いたが2通りは素通りした。

```
形式検査だけで「全件照合しました」とは言えない。
実在の確認は国税庁の公表システムに問い合わせて初めて成立する。
```

国税庁の公表システムへの問い合わせは実装してあるが、
**利用申請で発行されるアプリケーションIDが必要で、まだ実物で動かしていない。**

## 構成

```
core/   C++17。OpenCV 4.6 / Tesseract 5.3（jpn）/ poppler
        前処理・分割・OCR・項目抽出・正規化・照合

api/    Go 1.26。pgx / stripe-go
        HTTP API・ワーカー・判定・登録番号・入出金の突合・決済

web/    Rails 8.1 / Ruby 3.3。Devise
        承認キュー・閾値シミュレーション・監査ログ・影響範囲・入出金

db/     PostgreSQL 17。マイグレーションは手書きのSQL
        pg_trgm / pgcrypto
```

```
core/  約 3,400 行
api/   約 6,800 行
web/   約 3,100 行
```

### PostgreSQL の照合順序について

`pg_trgm` を日本語で使うため、DBの作成時に指定が要る。

```
LC_COLLATE=C  LC_CTYPE=C.utf8
```

`LC_CTYPE=C` だと `show_trgm('シラカワ商事')` が空を返す。
**エラーは出ない。** 候補生成が常に0件になるだけなので、気付くのが遅れる。
起動時に確かめる仕掛けを `db/init/` に入れてある。

## 動かす

```bash
cp .env.example .env    # 値を埋める
docker compose up -d postgres minio
```

C++ をビルドする。

```bash
docker compose run --rm core bash -c "cmake -S . -B build && cmake --build build -j4"
```

**この順番に意味がある。** Go の API は C++ の実行ファイルをプロセスとして
呼ぶので、`./core/build` に実行ファイルが無いと動かない。先にビルドする。

API とワーカー、画面を起動する。

```bash
docker compose --profile app up -d
```

画面は `http://localhost:53000`、API は `http://localhost:58080`。

### api コンテナが ubuntu を土台にしている理由

Go の公式イメージをそのまま使っていない。API は C++ の実行ファイルを
呼ぶが、それは `core`（ubuntu:24.04）でビルドされていて、そこの共有
ライブラリに soname まで結びついているため。

```
dm_preprocess → libopencv_imgcodecs.so.406 / libopencv_core.so.406 ...
dm_ocr        → libtesseract.so.5 / liblept.so.5
```

土台が違うと「実行ファイルはあるのに起動できない」形で失敗する。
エラーは C++ 側から出るので原因が分かりにくい。`api/Dockerfile` は
Go の道具一式だけを公式イメージから持ってきて、土台は core と揃えてある。

### 2回目以降は、これだけでよい

一度ビルドが済んでいれば、起動と停止はこの2つ。

```bash
docker compose --profile app up -d     # 起動
docker compose --profile app down      # 停止
```

C++ のビルドは要らない（`./core/build` に残っている）。
DB の中身も名前付きボリュームに残るので、前回の続きから始まる。

### 事務所を跨げないことを、その場で確かめる

```bash
cd api && go run ./cmd/tenanttest
```

事務所を2つ用意し、片方の署名でもう片方のあらゆる口を叩く。
30項目。**開発DBに対してだけ流すこと**（上の「検証用の事務所は、開発DBにだけ作ること」）。

```
① 署名そのものの検証          署名なし・鍵違い・時刻ずれ・本文差し替え・番号差し替え
② Aの署名でBのものを触る      伝票・承認・突合・表記・アップロード・取り込み・職員
③ 跨いだ後、Bのデータが不変   DBを直接読んで確かめる
④ Bの署名でBのものを触る      通ること
⑤ 記録が動かせないこと        DELETE も UPDATE も効かないこと
```

**②だけでは足りない。** 何を送っても失敗するなら跨ぎも当然失敗するので、
「拒否された」は守れている証拠にならない。1つの口につき、
跨いで拒否されることと、持ち主なら通ることを両方確かめている。

このツール自体が落ちることも確かめた。伝票の所有確認を1箇所外して走らせたところ、
`Bの伝票を読む → 200` を検出して終了コード 1 で落ちた。

### ネットが無くても動く

Go の依存は名前付きボリューム（`gomod`）に置いてあるので、`down` しても
消えない。**一度起動したことのある機体なら、その後はネットに繋がなくても
立ち上がる。** `GOPROXY=off`（ネットを一切使わない設定）でビルドが通ることを
確認済み。

これが無いと `down` のたびに依存が消え、`up` でネットから取り直しになる
（実測: 7件・69MB）。回線の使えない場所で見せるときに困る。

## どこまで作って、どこから作っていないか

**作りかけで止まっているのではなく、意図的に線を引いてある。**

動くのはここまで。帳票を入れると読み取り・照合・三分岐が動き、
閾値を変えると過去の全件が再集計される。銀行明細とカード明細を
取り込めば入出金と突合し、インボイス登録番号も全件検査する。
`docker compose` で一式が立ち上がる。

作っていないのは、**買う相手が決まってから作れば間に合うもの**。

```
本番への一式（R2 / 本番DB / デプロイ）   動かす先が決まってから決めることが多い
Stripe の本番キー                        テストモードで確認済み。課金する相手が要る
国税庁 公表システムの疎通                クライアントは実装済み。利用申請でIDが要る
入金側の消込                             受領側が圧倒的なので、実務での価値が薄い
DB層の行レベルセキュリティ（RLS）        分離はアプリ層で担保済み。追加の防御層になる
署名の使い回し防止（nonce）              5分の窓は時刻で塞いである。窓の中の再送は通る
```

下2つは「無いと危険なもの」ではなく「もう一段」に当たる。
入れ方は [設計上の判断](#設計上の判断) に書いてあるので、必要になった時点でその順で入れる。

測れていないものもある。こちらは判断ではなく、単に材料が無い。

```
実スキャン画像での検証        生成データ100枚と実物7ファイルでしか測っていない
上下に並べた紙の分割          誤って切る例は測れたが、正しく切る例が1枚も無い
```

正例が無い状態でしきい値を決めても、その値には根拠が無い。
だから `kMinGapH = 0.0` で無効にしてある。詳しくは
[docs/PROGRESS.md](docs/PROGRESS.md) の末尾に書いた。
